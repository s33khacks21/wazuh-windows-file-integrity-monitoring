## 1. Executive Summary

This report documents a controlled File Integrity Monitoring (FIM) exercise using Wazuh. The objective was to validate whether changes within a monitored Windows directory generated observable security events.

Three scenarios were tested:

1. Modification of an existing file.
2. Creation of a new file.
3. Deletion of a test file.

All three events were observed in the Wazuh dashboard. The modification alert included integrity metadata, including file size, modification time, and cryptographic hash values.

**Assessment:** The configured lab successfully demonstrated the three tested FIM detection behaviors. No conclusion about malicious activity can be drawn from these tests because the changes were intentionally generated by the lab operator.

## 3. Alert Findings

### Finding A — File modification

**Observed event:** `test-file.txt` was modified.

The expanded Wazuh alert contained:

- Rule ID: `550`
- Rule level: `7`
- Decoder: `syscheck_integrity_changed`
- Event type: `modified`
- Monitoring mode: `realtime`
- Changed attributes: size, modification time, MD5, SHA-1, and SHA-256

The first recorded modification showed the file size changing from 18 bytes to 44 bytes. Before-and-after integrity hashes were also recorded.

**Security relevance:** Unexpected changes to monitored files can indicate unauthorized modification or tampering. Hash differences help demonstrate that the file's recorded integrity state changed.

**Limitation:** A hash change does not identify the person or process responsible, nor does it prove malicious intent.

### Finding B — File creation

**Observed event:** `created-file.txt` was created inside the monitored directory.

Wazuh displayed a corresponding file-added event.

**Security relevance:** Unexpected file creation can be relevant when investigating newly introduced scripts, tools, configuration files, or other potentially suspicious content.

**Limitation:** File creation is common during normal computing activity. The filename and event alone are insufficient to determine whether a threat is present.

### Finding C — File deletion

**Observed event:** `created-file.txt` was deleted from the monitored directory.

Wazuh displayed a corresponding deletion event.

**Security relevance:** Unexpected deletion can be relevant when investigating possible tampering, removal of important files, or attempts to interfere with normal operations.

**Limitation:** The deletion alert alone does not establish who performed the action, why it occurred, or whether it was malicious.

## 4. Initial Triage

If these events appeared unexpectedly in a production environment, I would begin by validating the following information:

- Which endpoint generated the event?
- Which file was affected?
- What was the event timestamp?
- Was the file created, modified, or deleted?
- Which attributes or integrity hashes changed?
- Was the action expected or authorized?
- Were there related alerts around the same time?

I would then determine the file's purpose and importance before assessing potential impact.

The observed Rule 550 modification alert was Level 7 in this lab. That is useful alert metadata, but an analyst should not determine incident severity from the rule level alone. Context, business impact, and corroborating evidence matter.

## 5. Investigation Procedure

### Step 1 — Validate the alert

Confirm the endpoint identity, file path, timestamp, event type, and available integrity details. Check that the event corresponds to the expected monitoring scope.

### Step 2 — Establish a baseline

Determine what the file should contain and whether the change was expected. Where possible, compare its current state with a trusted baseline or known-good copy.

### Step 3 — Identify the source of activity

Use available Windows event logs and endpoint telemetry to investigate relevant user logons, process execution, and file activity. Correlate timestamps carefully.

Do not assume that Wazuh FIM alone identifies the process or user responsible for a change.

### Step 4 — Correlate other evidence

Look for related authentication events, suspicious process activity, additional file changes, or relevant network events. Determine whether the event is isolated or part of a broader pattern.

### Step 5 — Assess potential impact

Consider whether the file is sensitive, whether its integrity affects a service or application, and whether the change could affect confidentiality, integrity, or availability.

### Step 6 — Record the findings

Document the event details, evidence reviewed, relevant timestamps, working hypotheses, and outstanding questions. Distinguish observed facts from assumptions.

## 6. Recommended Incident Response

If the investigation suggested unauthorized activity, I would follow the organization's incident-response procedures.

**Containment:** If warranted, isolate the affected endpoint through an approved process while considering operational impact.

**Evidence preservation:** Preserve relevant alert details, timestamps, logs, and hashes. Avoid unnecessarily modifying the affected file or destroying potential evidence.

**Eradication:** Identify and address the underlying cause before removing unauthorized files or changing affected systems.

**Recovery:** Restore affected files from a trusted source when appropriate, validate their integrity, and confirm that required services operate correctly.

**Post-incident review:** Document the cause, impact, response actions, and improvements needed to reduce the chance of recurrence.

These are recommended response steps for a hypothetical suspicious event. No production incident, containment action, or recovery operation was performed as part of this controlled lab.
